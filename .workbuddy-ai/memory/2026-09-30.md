# 2026-09-30 工作日誌 — LabelBuddy AI

## 使用者提問：「現在的 APP 有用 AI 的是在甚麼地方」

我先做了完整盤查（不是憑印象回答），結果**挖出一個嚴重問題**。

### 盤查結果：AI 用在 3 處，全部是雲端 LLM

| 端點 | 位置 | 觸發 |
| --- | --- | --- |
| `/api/analyze-label` | 標籤分析 | 拍照或點示範標籤 |
| `/api/analyze-indicators` | 生理指標 | 「AI 深入分析」按鈕 |
| `/api/ask-health-question` | 健康問答 | 輸入問題 |

三處都走 `callAiModel()` → OpenRouter（Gemini 區域封鎖冷卻中）。
模型鏈三個都支援圖片輸入（實測查 OpenRouter `/models` 的 `input_modalities`）。

**不是 AI 的地方**：OCR（tesseract.js）／紅黃綠顏色（規則引擎）／百分比（後端算）／
慢性病提醒（模板）／食育學堂（靜態）／語音（Web Speech API）／稱謂（字串後處理）。

★ 這句話可以直接放進比賽報告：**AI 負責「怎麼說」，規則負責「是不是安全」。**

### 🔴 挖到的問題：同意閘門只裝了 1/3

```
/api/analyze-label        → allowCloud = localOnly === false   ✅ 有閘門
/api/analyze-indicators   → 無條件呼叫 callAiModel             ❌ 沒有
/api/ask-health-question  → 無條件呼叫 callAiModel             ❌ 沒有
```

前端 `VitalMetricsSection` 與 `HealthQASection` 也都沒檢查 `cloudConsent`。

**所以 App 對使用者說了三句不成立的話**：
1. 引導頁 `只用本機（完全不上網）`
2. `/api/privacy` 自述 `uploadsHealthInfo: false`
3. 私隱條款（我 09-29 寫的）「身體指標…不會上傳」

實際上選「完全不上網」的人，只要按「AI 深入分析」或問一個問題，
血壓、心跳、血糖、自覺症狀、以及他打的健康問題都會送到 OpenRouter。

★ 這是「**不會報錯、只會偷偷違背承諾**」的 bug —— 比當機更糟。
★ 比賽的「倫理、安全與私隱」佔 5%，而且章程把「隱瞞」列為直接取消資格。

## 使用者指示：補上閘門 ＋ 三種分析模式

原話：「補上閘門。把前端 OCR（tesseract.js）變成一個後備方案，
使用者同意雲端時直接把圖片上傳上雲端給 AI 分析，引導頁選擇要有 3 個：
直接雲端、本機 OCR 和 AI 分析、只在本機用 OCR 和本機規則引擎」

### 三個決定（我問、使用者答）

| 問題 | 使用者選擇 |
| --- | --- |
| 預設模式 | **直接雲端（圖片上傳）** |
| 雲端失敗時 | **自動改用本機 OCR 重試，並告訴使用者** |
| 上傳解析度 | **1600px** |

### 做了什麼

1. **資料模型**：`AnalysisMode = 'cloud_image' | 'cloud_text' | 'local_only'`
   取代 `cloudConsent: boolean`
   - 新鍵 `labelbuddy_analysis_mode_v1`
   - ★ 舊鍵遷移：`true`→`cloud_text`、`false`→`local_only`。
     直接蓋成新預設值等於**偷偷把「不同意上傳」的人改成「照片會上傳」**。
2. **後端閘門**：兩個端點加 `localOnly` 檢查，`true` 時直接走本機引擎
3. **拍照流程分流**（`sendImageForAnalysis`）：
   - `cloud_image` → 送壓縮圖，**不做 OCR**
   - `cloud_text` → OCR → 送文字
   - `local_only` → OCR → 本機引擎
   - 抽出 `postAnalyzeLabel()` helper；`localOnly` **一律由 mode 推導**，
     呼叫端不能自己傳（避免某分支忘了帶旗標）
4. **自動降級**：`cloud_image` 失敗 → 前端自己 OCR → 文字重送 → 結果頁顯示通知
   ★ 一定要告知：悄悄降級會讓使用者以為照片有被用到
5. **新元件**：`AnalysisModePicker.tsx`（引導頁與設定頁共用）
   常數集中在 `src/data/analysisModes.ts`（避免 App ↔ 元件循環引用）
6. **解析度**：`IMAGE_MAX_DIM_CLOUD = 1600`、`IMAGE_MAX_DIM_OCR = 1024`
   （OCR 的瓶頸在字元辨識，不在像素數）
7. **隱私文案全面改寫**：
   - 拿掉「照片從頭到尾都不會離開這台手機」（對 `cloud_image` 不成立）
   - 每個模式卡片直接寫「離開手機：照片／文字／無」
   - `/api/privacy` **移除 `imageNeverLeavesDevice`**，改列三模式 `uploads*` 旗標
   - `LegalNotice` 私隱條款第 1~3 條同步改寫
8. **設定頁**新增「AI 分析模式」區塊（收合時顯示目前模式）
9. **結果頁**的二選一開關改成「在設定裡改分析模式」按鈕
   （二選一涵蓋不了三種；而且在那裡切換看不到各模式的差別）
10. 順手修掉 `handlers.ts` 的預設年齡區間 `'70-79歲長者'` → `'未提供'`

### 新增的自動化檢查

`scripts/check-analysis-mode.ts`（12 項）—— **實際啟動伺服器**驗證：
- `localOnly: true` 時三個端點都必須回本機標記
- `/api/privacy` 必須誠實列出三模式、`cloud_image.uploadsImage === true`
- `imageNeverLeavesDevice` 必須已移除

★ 本機路徑完全離線，所以這支測試**不消耗任何 API 額度**。

## 🔴 找到並修掉的 2 個真 bug

### ① 營養素單位沒翻譯 → 英文介面顯示「2350 毫克」

`NutrientFactBars.factDetail()` 把 `fact.unit`（後端給的中文單位）**直接插進**
翻譯字串，**從來沒呼叫過 `unitName()`**。
那個函式一直存在、後端也一直在用，**只有前端漏了**。

### ② 營養素「方向」永遠是「上限」→ 給出錯誤的健康建議

`numericLimits` 混了兩種性質：
- **上限**（越低越好）：鈉、添加糖、飽和脂肪
- **目標**（越高越好）：膳食纖維、鈣、蛋白質

但 `normalizeNutrientFacts()` 把**全部**寫成 `direction: 'limit'`。後果：

# 第七輪：引導頁最前面加「語言閘門」

## 使用者原話
「在第一頁前加一個問中文和英文的頁面」

## ★ 關鍵設計決定：這一頁**不屬於編號流程**

我沒有把 `'language'` 塞進 `buildSteps()`，而是用獨立的 `languageChosen` 布林值。
**兩個理由缺一不可**：

① 在選語言之前，進度指示**該用哪種語言**本身就是錯的 ——
   預設是中文，對英文使用者來說那行字他看不懂。
② 總步數要等選完身分才確定（長者 9／其他 7），在這裡顯示數字只會誤導。

若塞進陣列，第一頁會變成「第 2 步，共 10 步」，**兩邊都錯**。
→ 結果：語言閘門獨立，第一頁仍然是「Step 1 of 9」。

## 其他設計決定

★ **題目兩種語言同時寫**（「請選擇語言」＋ "Choose your language"）：
  這是唯一一個「使用者可能看不懂當前介面語言」的畫面，
  只寫一種語言會讓另一方卡住。

★ **選項用母語名稱**（中文／English），不經 `t()`：
  不會因為切到英文就把「中文」翻成 "Chinese" ——
  看不懂當前語言的人才找得到自己的語言。這是語言選擇器的通用慣例。

★ **第一頁的「上一步」＝ 回到語言閘門**（選錯了能馬上改，不用走完再去設定找）。
  原本第一頁沒有返回鍵（`current > 0` 才顯示），已改成一律顯示。

★ 語言閘門**維持顯示預設選中**（中文深藍底）—— 因為 App 當下的狀態就是中文，
  誠實反映比假裝沒選好。
