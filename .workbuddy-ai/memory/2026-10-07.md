## ★ 兩個「第一次寫錯、但檢查腳本抓到」的地方

### 1. 補英文名時的正則把「分隔符」當成字串
用 `'([^'()]+)'` 掃 `targetNutrients`，它會把 `... '鈉 (Sodium)', '食鹽' ...` 中間的
**`', '` 當成一個引號字串**吃掉 → 後面的項目全被跳過。
19 個陣列只改了 2 個，而且**沒有任何錯誤訊息**（正是本專案最常犯的形狀）。
→ 改法：**先 `split(',')` 再逐項處理**，不要用會跨越分隔符的正則。

### 2. 括號裡不一定是英文名
`'味精 (L-麩酸鈉)'`（中文化學名）、`'亞硝酸鹽 (加工肉)'`、`'超量鈉鹽 (加速排鈣)'`
—— 照格式拆，英文模式就會把「L-麩酸鈉」當成英文名送出去。
→ 已全部改正（化學名併進中文那一半；中文解釋本來就在 `description` 裡）。

## ★★ 全案風險最高處：`deps` 必須搬進 `fetch`

原本 `worker.ts` 是 module 層 `const deps: CoreDeps = {};`。
KV 綁定在 **per-request 的 `env`**，module 層拿不到 —— 所以非搬不可。
⚠️ 更糟的是：Workers 會**跨請求重用同一個 isolate**，
共用一份可變的 `deps` 會讓不同請求互相看到對方的綁定（極難重現的 bug）。
→ 現在 `const deps = env.QUIZ_BANK ? { quizBank: makeQuizBankStore(env.QUIZ_BANK) } : {};` 寫在 `fetch` 內。

## ★ 三個設計決定（與計劃書不同或計劃書沒寫的）

### 1. 索引要帶 `labelKeys`（計劃書沒寫）
計劃書的索引只有 `{ version, ids[], updatedAt }`。
但「挑題」要問「有沒有跟這次標籤對得上的題」——
只有 ids 的話，每次請求都得讀**整個題庫**（上限 500 題 ＝ 500 次 KV read）。
KV 免費層 100,000 reads/日 → 一天只能撐 **200 次請求**。
→ 索引的每個 item 加上 `labelKeys`，**1 次 read 就能篩出候選**，再讀命中的那一題。
`labelKeys` 是出題當下就固定的內容，不會有「改了本體忘了改索引」的問題。

### 2. `createdAt` 放在題目層級（計劃書沒寫）
同步用 `?since=<ms>` 只回更新的題 → 就必須知道**每一題各自**的時間。
`bank:index` 的 `items` 存 `{ id, createdAt, labelKeys }`。

### 3. 前端 `since` 用**伺服器回的 `updatedAt`**，不是 `Date.now()`
用本機時間的話，裝置時鐘快幾秒就會**永久跳過**那幾秒內產生的題目。
且**成功合併之後才推進** —— 先推進再合併，中途失敗會永久漏題且不報錯。

## ★ GET 的查詢參數怎麼傳（計劃書沒寫）
handler 簽名是 `(body, headers, deps)`，**拿不到 URL**。
→ `worker.ts` 與 `server.ts` 都改成「**GET 的查詢參數放進 `body`**」，
  `body` 在這裡的意義就是「這次請求的輸入參數」。
⚠️ 兩邊必須做**完全一樣的事**，否則同一支 handler 在本機與線上行為不同。

## ★ 檢查腳本抓到的一個**探針 bug**（不是程式 bug）
`check-learn-card.mjs` 的 `runResultFlow()` 第一次導覽（為了設 localStorage）
用的是**上一輪的模式** → 跑 local_only 那輪時，那次載入還是 cloud_image，
