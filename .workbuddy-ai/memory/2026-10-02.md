### 2. 長者字體上限 20px → 24px

查證結果：全站**只有 5 種字級**：
`text-[12px]`×1（LegalNotice，刻意不縮）、`16px`×179、`18px`×49、
`19px`×17、`20px`×65 —— **合計 310 處**（不含 12px）。

`index.css` 的 `html[data-density='compact']` 把非長者縮小：
16→14 / 18→16 / 19→17 / 20→18。長者不縮，所以**目前最大 20px**。

**使用者決定**：**24px**（不是 24pt=32px）、**全部按比例放大**。
目標：19 / 22 / 23 / 24。

★ 實作不必改 310 個檔案 —— 只要新增 `data-density='large'` 模式，
  在 `index.css` 補 4 行。class 名稱保持不動。

## ★★ 我主動提出的衝突（這是這一輪最重要的判斷）

**「長者字體放大 20%」與「引導頁不用滾動」是互相拉扯的。**

- 使用者先前要求引導頁每頁都不用向下滾動（360×640 目標）
- 但字體放大 20% 後，同樣內容會高出約 20% → 原本剛好塞得下的頁面會溢出

**排程結論：字體放大必須排在引導頁壓縮之前**，
否則會先把版面壓到剛好，改字體後全部重做一次。

★ 而且引導頁文案**可以縮短**（不像商品名稱不能改）——
  真的塞不下時，改文案比硬壓版面好。

# 第二輪：六項調整（已完成、已上線）

## 使用者回覆的四個決定
1. 慢性病預設值「有高血壓、糖尿病、腎臟病、花生過敏」← **這是實測回報，不是要求**
2. 「測驗」分頁放在第一
3. 要「完全不換算、只呈現標籤原樣」
4. 一定要滾動時，用半透明向下箭頭方塊

## ★ 慢性病預設值的根因

`App.tsx:567` 寫死：
```ts
return ['hypertension', 'diabetes', 'kidney_disease', 'peanut_allergy'];
```
正好就是使用者看到的四項。改成 `[]`。

★ 我的判斷：這不是「貼心的預設值」，是**替使用者做健康宣告**。
  沒高血壓的人被預設勾了 → 每次掃描都用低鈉標準判斷 →
  得到不屬於他的警告 → 久了學會忽略警告（**警告疲乏**）。
  真的對花生過敏的人，可能以為那是系統示範而沒去確認。
  慢性病與過敏是**必須由本人確認**的資訊。

## ★★ 非食物標籤：根因在提示詞（不是前端）

`server/core.ts` 原本：
```
If image is blurry or cannot be recognized as a food label,
→ warning_title "⚠️ 標籤不夠清楚"
```
兩種失敗共用一個輸出。**後果比訊息不精確嚴重**：
使用者拍風景照 → 被告知「標籤不夠清楚」→ 以為自己手震 →
**反覆重拍同一個不是標籤的東西**。

→ 拆成 `photo_issue: 'blurry' | 'not_food_label' | null`。
→ 消費端：那張卡的按鈕改成「換一個東西拍」（說「再拍一次」是誤導）。

## ★★ 單位不換算連帶抓到的「會變成錯話」字串

`nutrient.amount` 原本是「**這包有** {value} {unit}」。
改成不換算之後，數字已經不是整包 ——
這句話會把「每 100 公克 800 毫克」講成「**這包有 800 毫克**」。

★ 這是本專案第 4 類 bug（「改了 A 忘了 B」）的典型形狀：
  改了資料的語意，但**文案還停留在舊語意**，而且不會報錯。
  → 已改為「{basis} {value} {unit}」。

## ★ basis 用代碼而非自由文字

`basis: 'per_100g' | 'per_serving' | 'whole_pack' | 'unknown'` ＋ `basis_note`。
後端以**白名單**正規化（非白名單一律 unknown）。

★ 為什麼不能用自由文字：模型可能回「每 100 公克」，
  而這個字串會直接流到**英文介面** —— 那就是「英文介面露出中文」的 bug。

★★ 又區分第三種狀態：**本機引擎完全沒有 basis 欄位**。
  它不解析標籤的計數基準 → 說「標籤未標示基準」是對標籤的**錯誤宣稱**
  （我們沒去看，不是它沒寫）→ 改說「**基準未確認**」，描述 App 自己的狀態。

## 長者字體放大

`index.css` 新增 `data-density='comfortable'` 規則：
16→19／18→22／19→23／20→24（×1.2）。
★ 只改 index.css —— App.tsx 本來就設 comfortable，只是先前沒有對應規則。

# 第三輪：CPU「控制代碼」100 萬 —— 診斷（與本專案無關）

## 使用者問題
「為甚麼我的 CPU 控制代碼高達 1000000，還一直加，是不是和這個項目有關」

## 結論：**與 labelbuddy-ai 完全無關**

兇手是 **`AndrowsStore.exe`（PID 8464）** —— **騰訊應用寶電腦版**
（`Androws`，Company=Tencent，Description=腾讯应用宝，v3.0.8100.1583，
裝在 `D:\Program Files\Tencent\Androws\Application\3.0.8100.1583\`）。

## 實測數據（2026-10-02 12:20~12:25）
| 對象 | HandleCount |
| --- | --- |
| **AndrowsStore (8464)** | **1,037,159** |
| 全系統合計 | 1,153,332 |
| → AndrowsStore 佔比 | **86.3 %** |
| 專案 node ×6 | 各 ~178–184 |
| msedge（預覽用） | 177–1,954 |
| WorkBuddyAI | 1,334 |
| 其他 Androws 行程 | 151–912（正常） |

- 洩漏速率：**約 260–400 handles/秒，單調遞增、從不回落**
- 行程啟動 11:31:42（開機 09:25:40）→ 洩漏**從啟動就開始**，非外部事件觸發
- `HasWindow = False`（背景常駐）；`PrivateMemory` 只有 111 MB
  → **典型 handle leak**：吃的是**核心集區**，不是使用者記憶體
  （所以看「記憶體」欄位完全看不出問題，只有「控制代碼」欄位會爆）
- 版本目錄 `3.0.8100.1583` 更新於 **2026-09-10**（近期更新後才出現）

## ★ 診斷方法（可重用）
1. `Get-Process | Sort HandleCount -Descending | Select -First 25`
2. **關鍵判別式：算「佔全系統 handle 的比例」** —— 單一行程吃掉 >50 %
   就是它，不用猜。
3. **取樣兩次以上算成長率** → 穩定遞增 = 該行程自身 bug；
   與外部事件連動 = 被觸發。
4. 拿 `Win32_Process` 的 `ExecutablePath` / `CompanyName` / `FileDescription`
   確認血緣。

## ⚠️ 環境坑（已踩）
- **WorkBuddy 的 PowerShell 工具只回 exit code，不回 stdout** →
  必須 `Set-Content -Encoding UTF8` 寫檔，再用 Read 讀。
- ⚠️ **PS 5.1 的 `Out-File` 預設 UTF-16LE** → Read 會判定為 binary 而拒讀。
  **一律 `Set-Content -Encoding UTF8`**。
- 沙箱內 `tasklist` / `wmic` 無輸出（被擋）；`reg.exe` 在黑名單 →
  查登錄檔用 PowerShell `Get-ItemProperty`。

1. 立即：結束 `AndrowsStore.exe`（背景行程、無視窗，不影響 應用寶 服務）
2. 根治：更新或解除安裝 應用寶（若平常不用）
