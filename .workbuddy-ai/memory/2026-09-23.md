## 實作內容

**其他檔案**

  （`ResultDisplay.tsx`、`PhysicalIndicatorSection.tsx`、`SeniorHealthQASection.tsx`）
  —— 不改會變成永遠為 false 的潛在 bug

## 關鍵除錯過程（值得記下來）
1. 先從 OpenRouter API 撈出 **14 個免費視覺模型**（過濾 pricing=0 且 input_modalities 含 image）
2. 用 Pillow 產生**有精確數字**的測試標籤（760x900，鈉 1980mg / 65mg 兩張），
   比生成圖可靠，可驗證模型有沒有讀對數字
3. 實測：只有 `inclusionai/ling-3.0-flash-vl:free` 穩定；gemma-4-* 與 qwen3.8-27b 持續 429
4. **踩坑 1**：ling 是推理型模型，`max_tokens` 給 2000 會被 1804 個思考 token 吃光 → JSON 截斷
5. **踩坑 2**：端到端實測 40 秒 / 140 秒（三次逾時後降級）。
   加上處理器層級計時日誌才發現：**成功的那些 2 秒回應是 OpenRouter 快取命中**，
   真實未快取請求要 45 秒以上。教訓：驗證延遲時必須在提示詞加唯一編號避開快取。
6. **解法**：`reasoning: { enabled: false }` + 提示詞明確字數上限 + `max_tokens` 900
7. 修正後端到端：**5721ms / 3138ms**，單次嘗試成功、不再逾時

模型多次把「鈉」寫成「鈣」（例：「每100克就有1980毫克鈣」）。
已在 SYSTEM_INSTRUCTION 加入術語區隔規則，修正後輸出正確。

- 端到端：泡麵 → red ✅、豆漿 → yellow ✅，皆 `analysis_mode: cloud_ai`、`cost=0`
- 延遲：3~6 秒（原本 40~140 秒）
- 輸出長度：164~230 tokens（原本 ~3000），也更適合語音朗讀

## 待決事項
`App.tsx` 不顯示 `analysis_mode`，長者無法分辨結果來自雲端 AI 還是本機備援引擎。

# 第六輪：查證「多開 OpenRouter 金鑰能否提高額度」

## 使用者問題
「我是不是可以通過增加 openrouter 的金鑰數量來實現省額度的機制」

## 查證結果：不行
OpenRouter 官方文件（`openrouter.ai/docs/api_reference/limits`）原文：
> "Making additional accounts or API keys will not affect your rate limits,
> as we govern capacity globally."

→ **額度是全域治理，不是 per-key**。多開金鑰無效；多開帳號也無效且違反 ToS。

## ⚠️ 更正我先前的錯誤陳述
我上一輪跟使用者說「50 次不是每天重置，是這把金鑰的總量」——**這是錯的**。
`GET /api/v1/key` 實際回應：
```
limit: 50, limit_reset: "daily", limit_remaining: 50   ← 這是 per-key 信用上限
free_model_daily_requests: { used: 35, limit: 50, remaining: 15 }  ← 這才是免費請求數
```
`limit_reset: "daily"` → **每日重置**。我初次判讀時把 `limit` 誤當成免費請求數了。

## 真正的額度分級（由「累計購買點數」決定）
| 累計購買點數 | 每分鐘 | 每日 |
| --- | --- | --- |
| 未購買 | 20 | 50 |
| ≥ 10 點數 | 20 | 1000 |

唯一合法提升方式：一次性購買 ≥ 10 點數（累計），每日上限 50 → 1000（20 倍）。
免費模型本身仍 $0/次，買點數只提高請求次數上限。

使用者現況：`is_free_tier: true`、`creditsPurchased: 0`、今日 `remaining: 15`（35 次是測試消耗）。

## 本輪實作
- `getOpenRouterQuota()`：查 `GET /api/v1/key`，快取 60 秒（查詢本身不耗免費額度）
- `/api/ai-status` 新增 `openrouterQuota` 欄位，回報真實用量
- `callAiModel()` 在 OpenRouter `remaining <= 0` 時直接跳過該供應商，省下註定失敗的往返
- README 新增「免費額度的真相：多開金鑰沒有用」章節

## 驗證
`/api/ai-status` 實際回應：
```json
"openrouterQuota": { "used": 35, "limit": 50, "remaining": 15, "isFreeTier": true, "creditsPurchased": 0 }
```

# 第七輪：查證「用其他 Google 帳號能否繞過區域限制」

## 使用者問題
「我用我其他的 google 帳號 可以嗎」

## 實驗設計
要判斷「區域檢查」發生在驗證流程的哪一階段，用四種請求對照：

| 請求 | 回應 |
| --- | --- |
| 完全不帶金鑰 | `403 PERMISSION_DENIED: Method doesn't allow unregistered callers` |
| 帶無效金鑰 | `400 API_KEY_INVALID` |
| 帶真金鑰 | `400 FAILED_PRECONDITION: User location is not supported for the API use.` |
| 無金鑰 generateContent | `403 PERMISSION_DENIED: unregistered callers` |

## 結論：換帳號沒有用
順序是「身分檢查 → 金鑰有效性 → 區域檢查」。
**未帶金鑰時不會出現區域錯誤**，說明區域檢查不是 pre-auth 的網路層阻擋，
而是在金鑰被接受之後，以**呼叫來源的位置**判定。
只要還是從同一個地方呼叫，換幾個帳號結果都一樣。

兩把不同金鑰得到完全相同的錯誤，也支持「與帳號/金鑰無關」。

## 真正能改變結果的做法
1. 把後端部署到支援區域（台灣／新加坡／日本）——合規，程式已支援
2. 改用無區域限制的供應商（OpenRouter，目前方案）
3. 改用中國大陸／澳門可用的供應商（阿里雲百鍊 Qwen-VL、智譜 GLM-4V 等）

⚠️ 以 VPN 或謊報帳號地區繞過屬服務條款問題，不建議。

## 附帶
使用者可能也想問「多開 Google 帳號拿更多 OpenRouter 額度」——
OpenRouter 官方已明說「additional accounts or API keys will not affect your rate limits」，
同樣無效且違反 ToS。已一併說明。
