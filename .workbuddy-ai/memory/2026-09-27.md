### ★★★ 四個必須先決策的架構衝突（本次最重要的發現）

**衝突 1：「本地 AI」在瀏覽器架構下做不到**
清單假設「手機 App 可讀 RAM／NPU／Android 版本並在本機跑 AI」，
但本專案是**網頁 App（Vite + React）+ Node 後端**：
- 瀏覽器**無法**讀 NPU（沒有任何 API）
- 瀏覽器**無法**讀 Android 版本
- `navigator.deviceMemory` 只有粗粒度（上限 8）且僅 Chrome 系列
- 瀏覽器實務上**無法**跑 LLM
→ 選項 A：走 APK 路線（12 天內不可能）；**選項 B：重新定義「本地」＝本機伺服器（筆電）**（建議）

**衝突 2：「雲端只收文字」與現有架構相反 —— 但這是好事**
現況：原圖 → 雲端**視覺**模型（`server.ts:981` `image: { base64, mimeType }`）
要求：原圖 → 本地 OCR → **文字** → 雲端文字模型
→ **同時解決三件事**：① 隱私（原圖不出門）② **免費解掉中文錯字問題**
（「鈉→鈦」是視覺模型要同時做 OCR + 推理造成的；拆開後文字模型可靠度大幅提升）
③ 速度與額度（文字 token 遠少於圖片）
→ **這是整份計劃裡最高價值、且完全免費的改動**

**衝突 3：「自動上傳」與「預設不上傳」矛盾**
清單說 RAM < 4GB → 雲端後備（自動上傳）；但我們的隱私預設是不明確同意就不上傳。
→ 解法：**首次啟動的同意畫面就是那個「明確同意」**，同意後才啟用自動分級。

**衝突 4：「人臉／姓名／學號／手部」可行性不一**
- 人臉：可用 MediaPipe Face Detection 在**瀏覽器端（上傳前）**偵測 → **拒絕處理**（比模糊化簡單）
- 姓名／學號：姓名無法可靠偵測；**號碼格式**可用規則比對
- **手部：不建議做**（拿標籤的手必然入鏡，擋掉會讓 App 完全不能用）→ 改成拍攝引導
